# Repack feasibility: one-shot read-only WAL and TOAST survey

## Purpose

Bob's private Render volume is approximately **687.8 MB / 1 GB** as of
2 November 2026. `public.bob_improvement_observations` is allocated
**66.84 MB**, with about **52.91 MB of TOAST allocation** and an estimated
zero dead rows in its main table. These statistics do **not** prove how many
MB can actually be reclaimed. The `pg_repack 1.5.3` client was verified
on the existing Push service and is not permitted to rewrite any table.

## One-time opt-in

Only setting `BOB_REPACK_SURVEY_ONCE=1` on the existing Push service enables
`storage_repack_survey.start_if_enabled()`. It starts one nonblocking
daemon after normal HTTP/push startup, performs two short **read-only**
database snapshots separated by 15 seconds, and emits exactly one sanitized
`BOB_REPACK_SURVEY` log. A normal deploy with the flag absent makes no
database calls from this module.

The target is a hardcoded allowlisted public table. Each SQL connection is
independent, has PostgreSQL default_transaction_read_only=on and
1500-ms statement / 250-ms lock timeouts; no transaction remains open during
the observation interval.

The report contains only:
- Total/heap/index/TOAST bytes as allocated, estimated live/dead rows in
  main table and TOAST, availability and installation status of the
  `pg_repack`/`pgstattuple` extensions, and whether the previously
  verified private `pg_repack` client is available
- Two cumulative `pg_stat_wal.wal_bytes` readings compared over
  approximately 15 seconds, provided their reset marker is identical and
  the count is monotonic; otherwise WAL is **not observed**
- Existing independent fresh Render physical volume usage, if available

**No** query reads user original JSON values, invoices, product identities,
trade data, original screenshots, credentials or archive keys. No extension
is enabled, no `pg_repack`, `VACUUM FULL` or DELETE issued, no external
database networking opened, and no new service created.

## Critical interpretation

`pg_stat_wal.wal_bytes` is cumulative WAL generated by the database. A
short 15-second positive delta shows observed traffic during that interval,
**not** the amount of currently occupied WAL files or a safe peak generation
budget. `pg_ls_waldir` was previously unavailable to the managed role;
we do not infer its size from the difference between database and volume.

Main- and TOAST-table `n_dead_tup` counts are estimates and may be stale.
Allocated TOAST bytes are not equivalent to bloat. If
`pgstattuple` is not already installed, a new, separately approved
extension setup would be required to measure approximate heap/TOAST free
space; the survey deliberately does not enable it or perform table scans.
Even an observed free-space percentage is not a guarantee of physically
returned Render bytes after repack.

**No** result from this one-shot survey can set `readyToRepack=true`,
authorize table changes or claim `diskBytesFreed`. A later actual
repack needs source-specific independent restore, measured bloat, live
WAL/scratch reserve and lock/busy-window evaluation, separately authorized
single-table maintenance and a provider-volume before/after comparison.
